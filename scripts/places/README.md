# Place rules for the hub map (D-041)

Which OpenStreetMap places each hub shows on the map. The design is `docs/design/hub-map/HUB_MAP_DESIGN.md`.

| File                                  | Kind                   | What it is                                                                         |
| ------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------- |
| `rules/rules.txt`                     | edit by hand           | One line per hub: confidence, place mode, OSM filters, Geoapify categories, notes  |
| `rules/slugs.txt`, `rules/cats.txt`   | edit by hand           | Hub order and categories; must match `supabase/seed/hubs.sql`                      |
| `place_kinds.json`                    | edit by hand           | Display kinds (label, lucide icon) and the base tag to kind map                    |
| `build_rules_json.py`                 | script                 | `rules/` to `hub_place_rules.json`                                                 |
| `hub_place_rules.json`                | generated              | Per-hub rules (612 hubs)                                                           |
| `gen_place_rules.py`                  | script                 | JSON, kinds and taginfo counts to the seed, the filter, the id registry and stats  |
| `taginfo_counts.json`                 | generated by the job   | Worldwide use counts per tag from taginfo (`places-taginfo.yml`)                   |
| `rule_ids.json`                       | generated, append-only | Stable rule ids and `rules_version`                                                |
| `filters.txt`                         | generated              | `osmium tags-filter` expressions (base tags only)                                  |
| `rules_stats.json`                    | generated              | Counts: rules, base tags, links, verified, dropped                                 |
| `../../supabase/seed/place_rules.sql` | generated              | Seed for `place_kinds`, `place_rules`, `hub_place_rules` and `hubs.place_mode`     |
| `extract_rules.json`                  | generated              | The rules the extract job evaluates (ids, tags, extra conditions, kinds)           |
| `extract_places.py`                   | script                 | Extract job: Geofabrik pick, rule evaluation, collector posts (slice 5)            |
| `test_extract_places.py`              | tests                  | `python3 -I -m unittest discover -s scripts/places -p 'test_*.py'` (needs shapely) |
| `regions.json`                        | edit by hand           | Named regions for the extract job: place tile ids                                  |
| `extract_request.json`                | edit by hand           | Push trigger for the extract job on branches other than main (staging only)        |

After editing anything by hand:

```sh
python3 -I scripts/places/build_rules_json.py
python3 -I scripts/places/gen_place_rules.py
```

Commit every changed file. CI (`place-rules` in `.github/workflows/ci.yml`) runs both and fails if anything differs.

To refresh the taginfo counts, run the **Places taginfo check** workflow by hand, download `taginfo_counts.json` from its artifact (or copy the counts from its log), put it in this folder and re-run the generator. A tag with fewer than 50 uses worldwide drops its rule (or, as an extra condition, its value); a rule whose tags all reach 50 is marked verified.

The seed needs the slice 3 schema (migration `20261122000100_places_schema.sql`: `place_kinds`, `place_rules`, `hub_place_rules`, `hubs.place_mode`, `hubs.geoapify_categories`). It runs after `hubs.sql` in `supabase/config.toml` (`db reset`) and in the seed steps of `migrate.yml` (staging and production).

## Extract job (slice 5)

`.github/workflows/places-extract.yml` runs `extract_places.py` (design §3.1):

1. `tiles` turns the region (`atlanta`, tile ids, or `queue`) into tile ids. Named tiles that are not `wanted` or due a refresh are skipped unless `force` is set. The queue keeps the server's order: tiles with no OSM run (wanted or filling) first, by demand, then refreshes.
2. `plan` picks, for each of 9 sample points per tile, the smallest Geofabrik extract holding it (`index-v1.json`), so a border tile takes both sides. Tiles sharing extracts form a group with one bounding box (the tiles plus 2 km).
   `budget` (D-042 slice 2) then keeps the tiles one run builds, in queue order: at most 12 tiles, 6 Geofabrik files and 6 GB (every extract counts, cached or not), no extract over 3 GB (HEAD `Content-Length`; an unknown size waits), and no more download bytes than the free disk allows (less 3 GB, over 1.25). The others wait with a reason (`budget`, `extract_too_big`; `size_cap` when the size check refuses), recorded with `place_tiles_set_queue_reasons` so the map can say why an area is still being mapped.
3. The workflow caches the extracts for the ISO week, runs `osmium tags-filter` with `filters.txt` (and a second pass for `landuse=residential`), cuts the group box with `osmium extract -s smart` and exports points, lines and polygons.
4. `evaluate` reduces polygons to an interior point and lines to their midpoint, evaluates every rule (semicolon lists match by "contains"), drops `access=private|no`, homes (`building=house|residential|apartments|detached|…`), unnamed features other than courts, pools, tracks, playgrounds and similar facilities (which get a name such as "Tennis court at Grant Park"), unnamed facilities inside `landuse=residential`, and unnamed pools without public access. Segments of one named path collapse to one row per 2 km cell; the same name and kind within 150 m collapse to one row. Each row goes to its own tile only; rows outside the requested tiles are dropped. Only the §4.3 tag allowlist is kept.
5. `post` sends batches of 1,000 to `POST /collector/ingest/places`, then `POST /collector/tiles/{id}/done`. A tile whose row count fell more than 30% against its last count is not finished.

Where it posts: staging for a dispatch (or a push of `extract_request.json`) from a branch other than main; production only for a dispatch from main with `production` typed into the input; the nightly schedule (03:17 UTC; refreshes of active tiles on Sundays only) only when the repository variable `PLACES_EXTRACT_SCHEDULE` is `production` and production's queue is not empty. A staging dispatch can add test tiles as wanted with `want_tiles` and lower the budget inputs.
