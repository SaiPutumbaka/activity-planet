### 2.1 Listing removal (public takedown for imported items)

D-040 promises "a 'Request removal' link on every item". Today that link is an email.

**Database (migration 62).**

- `listing_removal_requests`: `reference` (`RM-XXXXXXXX`), `event_id` (nullable, `on delete set null`), `source_id` (nullable), `url` (https, at most 2,000 characters; the listing or the source page), `scope` (`item` | `source`), `requester_name`, `requester_email`, `email_hash`, `relationship` (`organizer` | `venue` | `rights_holder` | `other`), `reason` (at most 2,000), `status` (`open` | `removed` | `rejected`), `resolved_by` (`on delete set null`), `resolved_at`, `resolution_note`, `contact_cleared_at`, timestamps. RLS on with no policies (service role only); moderators read through an RPC. No account is needed and nothing links the requester to an account, as with NCII.
- `submit_listing_removal(p_event uuid, p_url text, p_scope text, p_name text, p_email text, p_relationship text, p_reason text)`: anon and authenticated; security definer, `search_path = ''`. Rate limits: 3 a day per email hash, 200 an hour overall (`rate_limited`). It returns `{reference}`. It refuses `p_event` unless the event is `kind = 'imported'` (`not_imported`); a removal request for a member's plan goes through reports.
- `mod_listing_removal_queue(limit, closed)`, `mod_listing_removal_resolve(request, action removed | rejected | reopen, note)`. Both check `auth.uid()` and `is_moderator()`. `removed` with scope `item` sets `event_imports.removed_at` on every import row of the event (this is the column's first writer, so linked copies from other sources cannot republish the event), sets `events.moderation_state = 'removed'` and logs a `moderation_actions` row. Scope `source` also switches the `feed_sources` row off, adds its host to `collector_denylist` (`reason 'owner request <reference>'`) and sets the source's candidate to rejected and locked. `moderation_actions` gains the actions `listing_remove`, `listing_reject` and `source_remove` and the target kind `listing`.
- `mod_queue` (latest body: `20261224000100_coaching.sql`) gains a `listing_removal` branch with an SLA from `mod_sla_hours` (latest: `20261217000100_admin_panel.sql`, new key `listing_removal`, 72 hours). The 24-hour Ticketmaster removal rule is met by the source sweep and does not depend on this queue.
- `purge_listing_removal_contacts()` on pg_cron daily: contact, name and reason are cleared a year after a request closes. The reference, dates and outcome stay.
- The `scripts`/test that keeps `data/denylist.json` and `collector_denylist` in step (`test/denylist-sync.test.ts`) learns that rows whose reason starts `owner request` live only in the database. The collector reads them through a new `GET /collector/denylist` route before each run and merges them into its in-memory denylist. A host removed on request is then never fetched again, even from a city seed.

**Edge Function.** `supabase/functions/collector/routes.ts`: `GET /collector/denylist`, collector secret, answers names and match types only.

**Tests.** `supabase/tests/listing_removal.sql`: anon submit, the rate limits, `not_imported`, the moderator-only queue, removal of an item with a linked copy from a second source (the event stays down after a re-ingest of both sources through `collector_ingest_events`), source removal (row off, host denied, `source_url_check` refuses the host), contact purge after a year (with the clock faked through `created_at` and `resolved_at`). ### 2.2 Organizer claim of an imported source or event

**Database (migration 62).**

- `organizer_claims`: `id`, `user_id` (`references profiles on delete cascade`), `source_id` (nullable), `event_id` (nullable; a claim of a single event resolves to its source), `host` (the registrable domain being claimed, lower case), `method` (`meta` | `well_known` | `dns_txt` | `feed`), `token` (`ap-verify-` plus 24 random base32 characters; owner-only read), `status` (`pending` | `verified` | `failed` | `revoked`), `attempts`, `last_checked_at`, `verified_at`, `failure`, timestamps. RLS: the owner reads their own rows, and moderators read all rows. Writes go only through RPCs.
- `start_organizer_claim(p_source uuid, p_event uuid, p_host text)`: authenticated, account at least 24 hours old, 5 a day per user. The host must equal the source's URL host or its registrable domain (`source_url_host`), and must not be denylisted. It returns the token and the three proof instructions. A source that already has a verified owner refuses (`already_claimed`); a moderator can revoke that owner.
- `organizer_claim_check(p_claim)`: the owner asks for a check now. For `dns_txt` the Edge Function in item 2.3 answers at once. For the other methods it marks the claim due for the next verification run.
- `collector_claims_due(limit)` and `collector_claims_record(results)`: service role; the verification job reads and writes through them.
- `feed_sources` gains `organizer_id uuid references profiles on delete set null` and `organizer_verified_at`. A verified claim sets them.
- `mod_queue` lists verified claims for a look after the fact: verification is automatic, and a moderator can revoke.
- What a verified owner can do, through `organizer_source_update(p_source, p_args)` (owner or moderator): set the source's default hub (an active 18+ hub), hide or unhide single upcoming items (`event_imports.removed_at`, logged, reversible by the owner), switch the source off (stop listing), and add or replace a connected feed URL (item 2.4). The event page shows "Listed by the organizer" instead of "Listed from <source>". Imported events still rank below human-hosted plans (D-040). A claim does not turn imported items into RSVP-able plans; an organizer who wants RSVPs posts plans as a member.

**Account deletion.** `request_account_deletion` (latest body: `20261224000100_coaching.sql`) gains, marked "Migration 62": delete the caller's `organizer_claims`; switch off the sources whose `organizer_id` is the caller and only connected feeds (`origin = 'organizer'`), then null `organizer_id`. Upcoming events from those feeds are cancelled by the normal sweep, since the source is off and lists nothing. Claimed sources that the collector found itself stay on, with `organizer_id` set to null. The delete-account Edge Function (`supabase/functions/delete-account/index.ts`) needs no change, because none of these rows is in Storage; its comment lists the new tables.

**Tests.** `supabase/tests/organizer_claims.sql`: account age and rate limits, a host that does not match, a denylisted host, `already_claimed`, the owner-only token read (`set local role authenticated`, another user's JWT sees nothing), the verified path through `collector_claims_record`, owner updates (hub, hide, off) and a stranger's refusal, moderator revoke, account deletion (claims gone, connected feed off, found source kept with `organizer_id` null).

### 2.3 Ownership verification (shared by 2.2 and 2.4)

Three proofs, all free and all without a key:

1. **Page token.** `<meta name="activityplanet-verification" content="ap-verify-…">` on the claimed site's home page or the source page, or a file at `https://<host>/.well-known/activityplanet-verification.txt` that contains the token.
2. **DNS TXT.** A TXT record at `_activityplanet.<registrable domain>` with the token, read through DNS-over-HTTPS (`https://cloudflare-dns.com/dns-query?name=…&type=TXT`, `accept: application/dns-json`; public, no key, no account).
3. **Feed token** (connected ICS only). The token appears in the calendar's `X-WR-CALDESC`, `X-WR-CALNAME` or any `DESCRIPTION` of an upcoming event. This is the only proof a Google Calendar or Outlook public ICS can carry, since its host is not the organizer's.

**Where checks run.**

- DNS TXT runs in a new Edge Function, `supabase/functions/organizer-verify` (user JWT, `organizer_claim_check`). It contacts only the DoH resolver, never the claimed host, so it opens no SSRF path from the Edge runtime.
- Page and feed checks fetch the organizer's host, so they run in the collector package with the `PoliteFetcher` (https only, public hosts only, the connect-time address check, the denylist, size and time caps). The new `collector verify` CLI command (`packages/collector/src/verify.ts`, `src/verify-cli.ts`) reads `GET /collector/claims/due`, fetches at most 3 URLs a claim, and posts `POST /collector/claims/record`. A claimed site that disallows the bot in robots.txt still gets the verification request, because the owner asked for it. The request is limited to the single home page or `.well-known` URL and is logged as `verify`.
- A new workflow, `.github/workflows/collector-verify.yml`, runs every 30 minutes and on dispatch. Its first step asks the queue for its size and exits when it is 0, so an idle run costs about 20 seconds. It runs against staging, and against production only from `main` with `COLLECTOR_PRODUCTION=true`, with the same secret handling as `collector-ingest.yml`. Logs print counts and outcomes only, never a host or a token.
- A claim fails after 10 checks over 7 days (`failure` set to `token_not_found`, `dns_no_txt`, `fetch_failed:<reason>`). The owner can start again.

**Tests.** Collector: `test/verify.test.ts` with fixture sites (meta token, `.well-known`, a token in an HTML comment that does not count, a token in an ICS `X-WR-CALDESC`, a redirect to another host refused, private address refused, a 3 MB cap). Edge Function: `supabase/functions/organizer-verify/verify_test.ts` with a stubbed DoH response (a quoted and split TXT, the wrong token, NXDOMAIN, a resolver error that leaves the claim pending). SQL: covered by `organizer_claims.sql`.

### 2.5 Venue geocoding for imported events without coordinates

The geocoder tries three free steps in order, and keeps the result only when it lies inside the source's region.

1. **Our own places first.** For each location text, the collector reads the place rows of the source region's tiles (`GET /collector/tiles/{id}/rows`, already used by discovery) and matches by normalised name, with address tokens as a tie-breaker. The match uses the trigram threshold of `meeting_spot_refresh` (0.45) and must be within the region. A public `venues` row already used by a human-hosted plan with the same normalised name in the region also counts.
2. **Geoapify geocoding**, only when `GEOAPIFY_SERVER_KEY` exists (its terms allow storing results; D-024 already chose it for venues), within a new `collector_budget` key `geoapify_geocode_calls` (300 a UTC day). Without the key, this step is skipped.
3. **Nominatim** (`nominatim.openstreetmap.org/search`), following its usage policy: at most 1 request a second (the fetcher's API lane spacing set to 1.1 s for this host), the identifying User-Agent with the `/bot` contact URL, `format=jsonv2`, `limit=1`, `viewbox` set to the region's bounding box with `bounded=1`, `countrycodes` from the region's zone when known, no autocomplete, and at most 300 requests a night, which keeps it a small nightly batch. Every answer, hit or miss, is cached in the database (item below), so the same text is never asked twice within 180 days (90 for a miss). Photon (`photon.komoot.io`) is the fallback only when Nominatim answers 429 or 5xx, under the same 1 request a second and cache. Attribution: "Location © OpenStreetMap contributors" on the event page of a geocoded item (Slice 2). This runs only in the scheduled GitHub Action, never in clients or Edge Functions. D-041's "never from Overpass or Nominatim in production or from clients" is about sourcing places, so Slice 1 adds a dated amendment note to D-041 saying the nightly job may geocode imported venue strings within these limits. The note is Claude's call and Sai can reverse it. `meta.collector_geocode_nominatim` (`on` | `off`, default `on`) turns step 3 off without a deploy.

**Database (migration 63).**

- `venue_geocodes`: `key` (sha256 of the normalised location text plus the source region point rounded to 0.1 degree), `status` (`ok` | `miss`), `point`, `provider` (`place` | `venue` | `geoapify` | `nominatim` | `photon`), `place_ref` (an OSM ref or a places id, nullable), `confidence`, `checked_at`, `expires_at`. No user id. RLS on, service role only; moderators read counts through the health RPC.
- `import_location_key(location text, region_point geography)`: immutable helper, shared by SQL and tested against the collector's TypeScript copy with fixture strings.
- `collector_geocode_queue(p_regions text[], p_limit int)`: distinct location keys of upcoming imported events with `point_source = 'area_centroid'`, a location text that is not "Online" and is at least 4 characters, and no unexpired cache row. It returns `{key, location, region}` (the location text is public listing text, the region a rounded point and radius).
- `collector_geocode_record(p_results jsonb)`: stores the cache rows (at most 500 a call; every point is checked to lie within the region radius, else it is stored as a miss) and updates matching events: `approx_point` and `event_imports.point_source = 'geocoded'`. The check constraint `event_imports_point_source` gains `geocoded`.
- `import_upsert_batch` (latest body: `20261202000100_collector_ingest_fixes.sql`, marked "Migration 63"): when an item has no usable point, it looks up `venue_geocodes` by key before falling back to the area centroid, so a geocoded event keeps its point when its content changes.

**Collector and workflow.** New `src/geocode/` (`match.ts` places-first matcher, `nominatim.ts`, `photon.ts`, `geoapify.ts`, `run.ts`) and `pnpm --filter collector regions geocode`. It is a new step in `collector-ingest.yml` after `regions record`, with its own 8-minute budget. Routes in `supabase/functions/collector/routes.ts`: `GET /collector/geocode/queue`, `POST /collector/geocode/record`. `GET /collector/api-keys` also returns `GEOAPIFY_SERVER_KEY` when it is set (masked in the job as the other keys are). Logs print counts by provider and outcome only, never a location text.

**Tests.** `supabase/tests/venue_geocoding.sql`: the queue skips online, short, cached and already-placed items; record refuses a point outside the region; an event moves off the centroid; a later `collector_ingest_events` content change keeps the geocoded point; a miss expires. Collector: `test/geocode.test.ts` with a fake transport and clock (place match wins and sends no request, the 1.1 s spacing, 300 a night, the bounded viewbox, the User-Agent, Photon only after a 429 or 5xx, no-key Geoapify skip, a result outside the region refused, the key equal to the SQL helper on shared fixtures).

### 2.6 Collector health panel and stale or failing source alerts

  - sources by lane and state: enabled, off, probation, organizer-connected;
  - **stale**: enabled sources not seen for over 26 hours (slug, name, lane, hours);
  - **failing**: `collector_fail_streak >= 3` or `last_error` set (slug, streak, error class, never the error text with URLs);
  - each job's last run, and whether it is over 26 hours old (the 60-day schedule pause shows up here first);
  - regions not collected in 48 hours;
  - the age of the discovery gate pass and whether it has expired (30 days);
  - candidate outcomes over the last 7 days;

  - today's budgets (Ticketmaster, SeatGeek, Geoapify), and open listing removals and claims.
- Alerts: `notification_kind` gains `collector_alert` (`alter type … add value if not exists`, in its own statement before use). `collector_health_alerts()` runs on pg_cron hourly at minute 23. It computes the alert set (any stale job, at least 1 stale source, at least 1 failing source, an expired gate, a budget used up before 12:00 UTC) and calls `enqueue_notification` (latest body: `20261224000100_coaching.sql`) for every moderator, with `dedupe_key = 'collector_alert:<kind>:<UTC day>'`, so each alert reaches each moderator at most once a day. ### 2.7 City open-data connectors (Socrata SODA, ArcGIS Hub)

The adapters exist. What is missing is a way to find real event datasets for any region, and the datasets themselves.

**Change.**

- `data/opendata/*.json`: a registry of open-data event datasets, each with a `bbox`, a zone, `kind` (`socrata` | `arcgis`), the endpoint (`/resource/<4x4>.json` or `…/FeatureServer/<n>`), the field map, `geoColumn`, the licence name and URL, the attribution line, `verified`, and a `note`. Any collector region whose circle overlaps a dataset's bbox gets it as a lane 1 seed, the same way city files contribute seeds today, so a dataset in Calgary serves Calgary members without a city file. The seed test validates the registry (https, a licence named, attribution 10 to 300 characters, a field map with `title` and `start`).
- `pnpm --filter collector opendata scout --region <id>` (`src/opendata-scout.ts`) queries the Socrata Discovery API (`api.us.socrata.com/api/catalog/v1` and `api.eu.socrata.com`, free, no key) and the ArcGIS Hub search API (`hub.arcgis.com/api/search/v1`, free, no key) for datasets whose name or tags say event, festival, special event or calendar, inside the region's bbox. It prints dataset ids, names, domains, column names, licence and the latest row date. These are public metadata, so the public log may show them, but it never prints rows. A new dispatch-only workflow, `.github/workflows/opendata-scout.yml`, runs it. A person (or Claude in a later session) reads the output, opens the dataset's licence, and adds the dataset to the registry.
- An optional `SOCRATA_APP_TOKEN` (free, raises Socrata's throttling limit) is sent as `X-App-Token` when the repository secret exists, and is never logged. Without it requests go anonymous, which the SODA documentation allows at lower rate limits.
- A dataset is accepted only when it lists scheduled public events with a start date and its licence permits reuse with attribution (an open government licence, CC BY, CC0, ODC-BY or public domain). Permit registers that include private events (weddings, filming) are not accepted unless a column marks the event public, and the field map filters on that column (`where` in the field map, new).
- The two Atlanta placeholders are replaced by registry entries or deleted.

**Datasets to verify first.** These could not be confirmed from this environment (the container's network blocks `api.us.socrata.com`, `data.calgary.ca` and `hub.arcgis.com`; web search only returned portals, not dataset ids). ### 2.8 Eventbrite organizer OAuth (key-gated, no-op without its key)

D-040 rejects reading Eventbrite web pages and Eventbrite search. An organizer who connects their own Eventbrite account through Eventbrite's OAuth API is the organizer offering their data, which D-014 already allowed ("organizer-connected ICS and Eventbrite OAuth").

**Change.** A new Edge Function, `supabase/functions/eventbrite-connect`, handles `start` and `callback` with a state token bound to the user (`organizer_oauth_states`, 10-minute expiry). It requires `EVENTBRITE_CLIENT_ID` and `EVENTBRITE_CLIENT_SECRET` as Edge Function secrets. Without them it answers `{skipped: "no key"}` with status 200, and the app hides the button (`meta.eventbrite_connect` follows whether the secrets exist, reported through the health RPC). The token is stored in Supabase Vault (`vault.create_secret`, name `eventbrite:<user id>`), never in a table column, and is read only by a service-role RPC. Events come from the documented organizer endpoints (`/v3/users/me/organizations/`, `/v3/organizations/{id}/events/?status=live`) through the API lane of the PoliteFetcher (`apiAllow` gains `www.eventbriteapi.com/v3/` only, the denylist on `eventbrite` stays). They are ingested into an organizer-origin `feed_sources` row (kind `eventbrite`) by the nightly job. Eventbrite's API terms are re-read when the key is created, as D-040 asks for lane 1. Account deletion: the vault secret, the OAuth state rows and the source are removed in `request_account_deletion` (marked "Migration 62"), and the delete-account function revokes the token at Eventbrite when the key exists.

**Tests.** `supabase/tests/organizer_feeds.sql` (the token never readable by `authenticated`; deletion removes the vault secret), `supabase/functions/eventbrite-connect/connect_test.ts` (no key gives `skipped`; the state token is single-use and expires; a callback for another user is refused), `test/lane1.test.ts` (the Eventbrite API lane, its `apiAllow` entry, and that eventbrite.com web pages are still refused).

### 2.9 Discovery-queue tuning from the staging numbers

**Change (collector, recorded with migration 63).**

1. **Origin weight.** Wikidata candidates yield about 3 times as well as OSM ones (20% against 6.6%). Raise the Wikidata bonus from +10 to +25, and for the 50-id entity lookups, prefer OSM places that carry a `wikidata` tag.
2. **Kind priors** (`src/discovery/candidates.ts` `KIND_PRIOR`). Raise `community` from 0.5 to 0.7 (best yield). Lower `cinema` from 0.4 to 0.15 (0 of 19; showtimes live on ticketing sites) and `school` from 0.7 to 0.5 (3 of 37). Keep `library` at 0.8 (1 of 16 in Atlanta, where the big systems are BiblioCommons without feeds, but LibCal and Communico libraries elsewhere carry feeds). Leave the rest unchanged until a second region has data.
3. **Learned yield.** A view, `source_kind_yield`, over `source_candidates` across all regions (kind, origin, probed, good) is exposed to the job through `GET /collector/discovery/yield`. Once a kind has at least 30 probes worldwide, the cheap score uses `max(0.1, (good + 1) / (probed + 5))` in place of the static prior. A test pins the static priors as the fallback.
4. **Record what failed.** `source_candidates_record` (latest body: `20261214000100_discovery_review_fixes.sql`, marked "Migration 63") keeps `platform` on rejected candidates, so the yield view can show which platforms fail (today every rejected row has `platform` null).
5. **Stop re-probing dead kinds.** A candidate rejected `no_events_in_region` twice is locked for 180 days instead of retried every 30 days when its kind's learned yield is under 5%.
6. **Queue order.** `source_discovery_probe_queue` (latest body: `20261214000100_discovery_review_fixes.sql`) orders by the stored score, then Wikidata first, then fewest previous probes. The 150-a-region daily cap and the 10-new-regions cap stay.

These changes alter the probe code hash (`src/discovery/version.ts`), so the Atlanta gate has to pass again before probes resume. That is the existing rule, and `discovery.yml` runs the gate on the branch push.

**Tests.** `test/discovery-probe.test.ts`: the new priors and bonus, the learned-yield switch at 30 probes, the lock after two empty probes of a low-yield kind. `supabase/tests/discovery_tuning.sql`: the yield view's counts, platform kept on rejection, the queue order, the 180-day lock. Gate: the `discovery.yml` gate run on the branch must pass (at least 6 of 9 Atlanta seeds).

## 3. Work queue: skip pgmq

pgmq is free, but nothing here needs it.

- Every queue in this plan is a query over state the tables already hold: claims due, geocode keys not cached, regions due, candidates due. Each has one consumer, a scheduled GitHub Action that runs once at a time (workflow `concurrency` groups). The existing pattern, `for update skip locked` with a lease (as `claim_pending_notifications` and `places_fill` do), covers retries.
- pgmq adds a second copy of state to keep consistent with the tables, messages to purge, and grants on the `pgmq` schema for every role. It adds no capacity we lack: the bottleneck is the politeness spacing per host, not dequeue throughput.
- **Revisit when** two or more consumers need the same work at once (for example, Edge Functions and Actions both collecting), or when a queue goes over about 10,000 rows a day.

### 4a. Slice 1 as built (2026-11-05): corrections to this plan

Built on branch `main-r1pc3k`: `20261226000100_collector_completion.sql` (62, 2.58) and `20261227000100_collector_health_geocode.sql` (63, 2.59), the six staging tests (all green on staging), the collector package, the collector routes, `organizer-verify`, `eventbrite-connect` and the workflows. Where the plan above was wrong or could not be followed, the build did this instead:

1. **Public form (2.1).** `submit_listing_removal` is service role only, with a `p_client_hash` (5 a day per client), like `submit_takedown_request` since migration 54: the site's form route calls it after a Turnstile check (Slice 2). Granting it to anon would reopen the hole migration 54 closed.
2. **Withdrawing items (2.1, 2.2).** There is no "normal sweep" that cancels the items of a source that is off. `feed_source_withdraw` does it: `stop` cancels upcoming items as no longer listed (they come back if the source is read again), `remove` marks every import row removed and the events removed. Used by owner stop, moderator revoke, account deletion and source removal.
3. **Shared calendar hosts (2.1).** A source removal never denylists a shared calendar host (Google Calendar, Outlook, Yahoo, iCloud, the Eventbrite API): only the source is switched off and marked denylisted. `GET /collector/denylist` returns those sources' slugs too, and the collector skips them.
4. **robots.txt (2.3).** The verify job obeys robots.txt like every collector request (D-040 keeps it); a site that keeps the bot out reports `fetch_failed:robots_disallowed`, and the owner can use the DNS proof.
5. **Extra columns and arguments (2.2, 2.4).** `feed_sources` also gained `organizer_claim_id`, `organizer_hub_id` (the owner's hub survives the seed's hub tags), `organizer_stopped_at` (a stop survives a staging `--enable` run), `organizer_images_at` and `collector_region_id`; `organizer_claims` gained `feed_url`, `check_requested_at` and `reviewed_at`. `start_organizer_claim` takes `p_method` and `p_feed_url` (migration 66: a feed claim on a found source is always on that source's own ICS feed, and a feed claim's host is the feed's; `organizer_claim_target` says `feed_proof` and never returns the URL, which stays moderator-only; `collector_claims_due` fails claims whose host was denylisted since, and the verify job merges the database-only denylist; public logs print only the host of an organizer-connected feed or a hosted calendar service); `connect_organizer_feed` takes `p_lat`, `p_lng` for the point the owner picks; `my_organizer_claims` returns the token to its owner only (the column is not readable by `authenticated`); `mod_organizer_claim_review(claim, ok | revoke)` is the moderator's look after the fact, and `mod_queue` lists verified claims nobody reviewed (SLA key `organizer_claim`, 168 hours).
6. **`collector_ingest_events`** is rebuilt twice: in 62 for organizer rows (first good run enables, stop holds, the owner's URL, name, hub and image licence stand, Refresh now is cleared, an `org-` slug is never created by the ingest) and in 63 for the failing streak.
7. **Eventbrite (2.8).** The events are read inside `eventbrite-connect` (`{op: "sync"}`, called by the nightly job with the collector secret), so tokens never leave Supabase; the collector package only gained the `apiAllow` entry. A third secret, `EVENTBRITE_REDIRECT_URI`, is needed. The function's `{op: "status"}` tells the app whether the keys exist (no `meta.eventbrite_connect`). Eventbrite has no token revocation endpoint: account deletion removes the token from the vault, and the delete-account comment says so.
8. **Geocoding (2.5).** Nominatim requests are spaced 2 seconds apart (the collector's rule, stricter than the 1.1 s planned). `countrycodes` is not sent: the region's bounded box already limits answers. `collector_geocode_queue(p_limit)` takes no region list (it covers every upcoming centroid item). The places-first step matches the tile rows only; public `venues` rows are not reachable from the job without a new route and were left out. Geoapify uses the budget key `geoapify_geocode` (`collector_api_budget_cap` rebuilt, 300 a day).
9. **Alerts (2.6).** The dedupe key is `collector_alert:<alert>:<UTC day>:<moderator id>`, because `notifications.dedupe_key` is unique across people.
10. **Open data (2.7).** The ArcGIS Hub search ignored the box (the same 400 survey, permit-form and planning layers for every region), so it finds nothing near a region; the Socrata catalogue has no place filter, so the scout asks each candidate one `count(*)` inside the box and lists those with at least 3.
