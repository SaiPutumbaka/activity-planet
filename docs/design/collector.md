# Event collector (D-040)

`packages/collector` (`@ap/collector`) collects nearby public events so people can use the app the day they sign up, anywhere. It is TypeScript on Node 22, has no database access of its own, and runs as a scheduled GitHub Actions job (`.github/workflows/collector-ingest.yml`) that posts each source's complete item set to the collector Edge Function, which calls `collector_ingest_events` and through it `import_upsert_batch` (see [Ingest](#ingest)).

```sh
pnpm --filter collector collect --region atl --list      # seeds and API lanes that would run; no network
pnpm --filter collector collect --region atl --dry-run   # fetch, parse, normalize, print counts
pnpm --filter collector collect --regions-file regions.json --dry-run --json
COLLECTOR_SECRET=… pnpm --filter collector collect --region atl \
  --ingest https://<ref>.supabase.co/functions/v1/collector --enable   # post (staging)
```

Exactly one of `--dry-run` and `--ingest` is required (exit code 2 otherwise). The CLI never holds a database credential: `--ingest` only reaches the collector Edge Function with the collector secret.

## Pipeline

```
regions ─┬─ city seed files that overlap them ─┬─ PoliteFetcher (https, denylist, login check,
         │                                     │   robots.txt, 2 s per host, conditional GET,
         └─ API adapters that have a key ──────┘   timeout, size cap)
                       │
                lane parsers ── RawEvent ── normalize() ── ImportItem
                       │
     radius filter ── run window ── dedupe ── one SourceBatch per source ── Ingest (dry run or POST)
```

- **Input** is a list of regions (`{id, label, lat, lng, radiusKm, timezone?}`). `--region atl` uses the region in `data/cities/atl.json`. `--regions-file` takes the areas people actually use the app in, so coverage follows users. Every city file whose circle overlaps a requested region contributes its seeds. API adapters run once per requested region.
- **Output** is one `SourceBatch` per source: the item set `import_upsert_batch` takes (`external_id, title, description, starts_at, ends_at, all_day, location, lat, lng, url, cover_url, is_free, price_text, categories, host_org, open_to_public, cancelled, raw`, the shape of `supabase/functions/import-feed/adapters.ts`), plus two fields the RPC ignores, `attribution` (the source line to show) and `lane`. Skip counts are kept per reason.

### Discovery: what a page link may lead to

`src/parse/links.ts` classifies every link before anything fetches it.

- **Google Calendar** pages are never followed. A subscribe or embed link that names a public calendar (`cid=` or `src=`, as a calendar id or base64 of one) becomes Google's documented public address, `calendar.google.com/calendar/ical/<id>/public/basic.ics`. A `cid=` that wraps a feed on another site (`webcal://…`, `https://…`, or base64 of either) becomes that feed. `action=TEMPLATE` "add to calendar" buttons, private addresses and every other Google Calendar page are skipped. Outlook and Yahoo add-to-calendar links are skipped too. The resulting URL still goes through robots.txt, the denylist and the other fetcher checks.
- **Action pages** are skipped: Localist `/event/<slug>/confirm`, `/register`, `/rsvp`, `/edit` and the like, `/event/create`, `/events/new`, `/submit`, and sign-in or sign-up paths. They never list events, and sites usually disallow them in robots.txt, so following them only cost requests.
- **The source's own feed comes first.** Feeds are ranked: the page's `<link rel="alternate">` feeds, then calendar-wide export links, then single-event exports (`/event/<slug>/?ical=1`). When a calendar-wide feed yields events, single-event exports and the discovered event pages are not fetched. A seed can set `"crawlPages": true` to crawl the pages anyway. A seed of kind `ics`, `rss` or `localist` is never crawled at all.
- Skipped links are counted by reason in the run's `linksSkipped`.
- **A feed that says noindex is never read, and the source's pages are read instead.** The Events Calendar (WordPress) sends its `?ical=1` export with `X-Robots-Tag: noindex`, while its HTML views and single event pages are usually indexable and carry schema.org Event JSON-LD. When no feed on a page seed yields events (none offered, or skipped for noindex), the collector reads the calendar's listing views that the page links to (`/<slug>/list/`, `/<slug>/month/`, with `/page/N/` or a date, or `?eventDisplay=list`; at most 3 per seed), or, when it was a calendar-wide TEC export that said noindex, its list view (`/<slug>/list/`, then `?eventDisplay=list` if that is a 404). An `ics` seed whose TEC export says noindex falls back the same way. Listing views are read for their own markup and their event links (TEC's event title links are recognised by class, so `/offstage/<slug>/` works too), never their feed links. Then the seed's event pages are read, single `/event/<slug>/` pages first, up to `maxPages`, skipping pages whose events a listing's own markup already gave (unless `crawlPages`). Every page is judged on its own `noindex`, `nosnippet`, `max-snippet` and `nofollow`, and the per-host request cap and run deadline below end the seed early.

A `localist` seed reads `https://<calendar>/api/2/events?days=<window>&pp=100&page=N` (filters such as `type=` in the seed URL are kept), through the normal web politeness: robots.txt and 2 s spacing, not the API lane. Private events and academic-calendar deadlines are dropped. If robots.txt disallows the API, the seed falls back to reading the calendar's home page like a page seed.

### What a lane reads

- **Facts only**: title, start and end, place (name, address, point), status, price or free, organizer, categories, and the link. The description is kept as a verbatim excerpt of at most 280 characters, cut at a word boundary.
- **No images** unless the seed says `"imagesLicensed": true`. Otherwise `cover_url` is always null, including from the APIs.
- **No LLM reads page text**, and nothing outside schema.org markup, feed fields or API fields is read.
- **ICS**: TZID (IANA names, mozilla-style prefixes, VTIMEZONE `X-LIC-LOCATION`, common Windows names), floating times in `X-WR-TIMEZONE` or the region's zone, all-day dates with an inclusive end, `DURATION`, `RRULE` (DAILY, WEEKLY, MONTHLY, YEARLY with INTERVAL, COUNT, UNTIL, BYDAY with ordinals, BYMONTHDAY, BYMONTH, BYSETPOS, WKST) expanded in wall-clock time within the run window (default 60 days, at most 200 emitted instances per event; rules without COUNT skip straight to the window however old DTSTART is, past RDATEs never count toward the cap, and each file gets a fixed expansion budget of 50,000 steps), `EXDATE`, `RDATE`, `RECURRENCE-ID` overrides including cancelled ones. `CLASS:PRIVATE` and `CONFIDENTIAL` events are dropped. BYHOUR, BYMINUTE, BYWEEKNO and BYYEARDAY rules give only DTSTART.
- **RSS/Atom**: an entry counts only when it carries event times (`ev:startdate`, `<start>`, `xcal:dtstart`, or hCalendar `dt-start` in the description). `pubDate` is never treated as an event time, so a news feed yields nothing.
- **Status**: cancelled events are sent with `cancelled: true`, so the RPC marks them cancelled. `EventPostponed` and date-TBD API events are dropped.

## Politeness

All of it lives in `src/net/fetcher.ts`, and nothing else in the collector touches the network.

- User-Agent `ActivityPlanetBot/0.1 (+https://activity-planet.vercel.app/bot)`, with no email. The `/bot` page still has to be written.
- **robots.txt** (RFC 9309) is fetched once per host per run, and conditional GET keeps it cheap across runs. The group for `ActivityPlanetBot` beats `*`. Within a group the longest match wins, and Allow wins a tie. `*` and `$` work. A 4xx means no rules. A 5xx or a network failure means nothing is fetched from that host (`robots_unavailable`). `Crawl-delay` is honoured when it is longer than 2 s. A delay over 60 s is waited out too, inside a per-host budget for the run (`--slow-host-minutes`, default 10): the host gets `floor(budget / delay) + 1` requests at that spacing, and later ones are skipped as `crawl_budget_spent`. A delay longer than the whole budget skips the host (`crawl_delay_too_long`). Keep `maxPages` small on such a seed. The API lane does not read robots.txt, because the API terms govern it.
- **At most one request per 2 seconds per host**, measured from request start to request start. Seeds run four at a time, and per-host spacing still holds across them.
- **Conditional GET**: ETag and Last-Modified are stored in `.cache/http.json` (gitignored; the Actions job can keep it with `actions/cache`), and a 304 is served from the cache. API-lane responses are never cached, because their URLs carry `apikey=` and `client_id=`.
- **Per-host request cap**: at most 60 requests to one host per run (`--max-requests-per-host`), robots.txt and redirect hops included. Later requests to that host are not sent (`host_budget_spent`), and the seed stops there.
- **Run deadline**: no request starts after `--max-run-minutes` (default 9), and a spacing or Crawl-delay wait that would end after it is not waited out (`run_deadline`). With 20 s timeouts and hosts that hang, the run still ends in time. The Atlanta seed file's worst case (every page offering a noindex export, list and month views and 60 event links) takes about 100 s of simulated time and stays under every host's cap (`test/tec.test.ts`).
- **Limits**: 20 s timeout, 3 MB body cap (bigger bodies are abandoned mid-stream), at most 5 redirects, and binary content types are refused. By default each page seed follows up to 10 discovered feeds and 25 discovered event pages (`--max-pages`, or `maxPages` per seed).
- **Every hop is checked**: https only (http links are upgraded, `webcal:` is read as https), port 443 only, public hosts only, denylist, and login-URL patterns. A redirect to a denied, private or login URL ends the fetch, so the target is never requested. Custom request headers never follow a redirect to another host, and an API-lane redirect must land on another `apiAllow` endpoint.
- **Public hosts only** (`src/net/address.ts`): IP literals in loopback, private, link-local (cloud metadata), CGNAT, unique-local, multicast, documentation and unspecified ranges (IPv4-mapped, NAT64 and 6to4 forms too) are refused, and so are `localhost`, `*.local`, `*.internal`, `*.home.arpa` and other private-use names and single-label hosts. The default transport is an undici `Agent` whose DNS lookup refuses a name if any address it resolves to is in those ranges, so the check also runs at connect time for every hop and defeats DNS rebinding.
- **Page permissions**: `<meta name="robots">` and `<meta name="activityplanetbot">`, plus `X-Robots-Tag` (unprefixed or prefixed with our bot name). `noindex` means no events are read from the page or feed. `nosnippet` (or `max-snippet:0`) means items carry no excerpt, and `max-snippet:N` clips the excerpt to N characters; the strictest value across the header and meta tags wins. `nofollow` means no links are discovered from the page, and `rel="nofollow"` anchors are never followed. Pages with a password field or a login form are skipped, and so are 401 and 403 responses.

## Denylist

`packages/collector/data/denylist.json` lists sites whose terms forbid automated collection or that sit behind logins. Today that is facebook.com, instagram.com, threads.net and threads.com, meetup.com, linkedin.com, joinhandshake.com, x.com, twitter.com, tiktok.com and their short-link domains (fb.me, m.me, lnkd.in, t.co, meetu.ps), evbuc.com, plus `eventbrite`, `ticketmaster`, `livenation`, `seatgeek` and `nextdoor` under any suffix. `domains` entries match the domain and every subdomain. `anyTld` entries match when the name is the site's own label: second to last, or third to last under a two-part suffix such as co.uk or com.au (so `eventbrite.events` and `nextdoor.com.au` match, `eventbrite.example.org` does not). `apiAllow` is the only way onto a listed site, and only for the API lane. A URL on the list is never requested, whether it comes from a seed, a discovered link or a redirect. Linking out to such a page from an item (a Ticketmaster event URL from the Discovery API) is fine, because nothing fetches it. Add entries as data. Removing one needs an entry in `docs/DECISIONS.md`.

## Normalization (the `import_upsert_batch` constraints)

`src/normalize.ts` applies the same rules as the RPC, so dry-run counts match what the database would accept:

- The title is whitespace-collapsed and entity-decoded. It must be at least 3 characters and is clipped to 120 with an ellipsis.
- The description is the excerpt above (at most 280; the database allows 2000).
- The URL must be https and at most 2000 characters. When the event has no link of its own, the page it is listed on is used, or the first https link in an ICS description. Otherwise the event is skipped (`no_https_url`).
- `starts_at` and `ends_at` are UTC ISO instants. Floating and date-only times are read in the source's zone (API venue zone), else the region's zone. A missing or non-positive end becomes start + 2 h, or the end of the day for all-day items. Spans over 3 days are skipped (`longer_than_3_days`).
- `location` is at most 120 characters ("Online" for online-only events), `price_text` at most 40, and `host_org` at most 120. Categories are de-duplicated, at most 10.
- `lat`/`lng` are kept only when they are valid and not 0,0.
- `external_id` is the source's UID, `@id` or API id. For a recurring instance it is `<uid>#<instance start>`. Ids from a discovered feed get a `f<hash>:` prefix and ids from page markup get `p:`, so feeds of one source cannot collide. An id longer than 200 characters becomes a hash.

After normalization:

- **Radius**: an item with a point is kept only inside one of the requested regions. An item without a point is kept only when its source's own area (the seeded city's centre, or the region an API was asked about) lies inside one of the requested regions, and the RPC places it on the fallback centroid. A small user region at the edge of a city therefore does not get the city's coordinate-less events.
- **Window**: an item is dropped when it has already ended or starts after the window.
- **Dedupe within a source**: the same external id, the same title (letters and digits only) and start minute, or the same URL and start minute, listed twice by one source. Copies of one event from two sources are all sent (migration 38): `import_upsert_batch` links them with the same key (`import_title_key` and the start minute, or the URL and the start minute), so each source keeps seeing its own copy and none is cancelled as unlisted. Batches post in lane order (official feeds, then APIs, then page markup), so the official copy usually makes the event.
- **Seen ids**: the external ids a source still lists that the run does not send (outside the regions, past the window, a duplicate within the source) go with the batch as `seen`. The RPC counts them as listed (`listed_not_sent`), so an event moved past the window is not cancelled for it.

## Adding a city

1. Copy `packages/collector/data/cities/atl.json` to `data/cities/<id>.json`. Set `region` (`id` of 2 to 40 characters from a-z, 0-9 and `-`; centre; `radiusKm` up to 300; IANA `timezone`).
2. Add seeds. Each needs a unique `id`, a `kind` (`page`, `ics`, `rss`, `localist`, `socrata`, `arcgis`), an https `url`, a `name` (2 to 80 characters), and an `attribution` line (10 to 300 characters, naming the source and its host). Optional: `host_org`, `categories`, `hubs` (at most 5 hub slugs; the first active 18+ one is the source's default hub), `discover: false`, `maxPages`, `crawlPages`, `imagesLicensed`, `enabled: false`, `verified`, `note`. Set `verified: true` only once a live run has read the endpoint or a person has opened it; say why in `note`, and say why a seed is off.
   - Good page seeds are the events pages of the library system, parks department, museums, university public calendars and city or county sites. Discovery finds their feed exports and event pages.
   - Prefer a feed seed (`ics` or `rss`) when the source publishes one. It is one request, and the data is the source's own. Platforms with documented public feeds: Localist (`kind: "localist"` with the calendar's `/api/2/events`), The Events Calendar for WordPress (`<calendar>/?ical=1`), Trumba (`trumba.com/calendars/<web name>.ics`), CivicPlus (`/common/modules/iCalendar/iCalendar.aspx?catID=<n>&feed=calendar`), LibCal (`ical_subscribe.php`), and Communico's RSS export where the library has turned it on.
   - A site that answers the bot with 401 or 403 stays off (`enabled: false`) until its owner offers a feed or allows the bot.
   - Open-data seeds need `fields` (`title`, `start`, plus `end`, `location`, `url`, `id`, `lat`, `lng`, `category` as available; dotted paths work), and `geoColumn` for Socrata circle filtering.
   - Never add a page that needs a login, a denylisted site, or a paid API.
3. Run `pnpm --filter collector collect --region <id> --list`, then `--dry-run`. Every blocked or unreadable seed shows up as a `skip … <reason>` line on stderr, and each source's `[dry-run]` line ends with `errors={…}` by reason. Add `--diagnose` (the dry-run workflow always does) for one stderr line per request: source id, URL with secret-looking query values redacted, HTTP status, the host the redirects ended on, media type, byte size, robots.txt verdict and the parser's verdict (`ics vevents=N events=N`, `rss items=N events=N`, `html jsonld events=N microdata events=N feed links found=N page links found=N`, `html no-event-markup jsonld blocks=N types=… hints …` (the page hints are fixed words, host names and counts: `wordpress`, `tec`, `tec-rest`, `wp-rest`, `nextjs`, `nuxt`, `js-app-root`, `noscript`, `iframes=<hosts>`, `script_hosts=<other sites' hosts>`, `anchors=N`, `event_path_anchors=N`), `not_a_feed detected=html`, `fetch_failed reason=…`, `not_requested reason=…`). It never prints item titles, descriptions or page text. A feed seed or a feed export URL (`?ical=1`, `.ics`, `iCalendar.aspx?catID=`) whose body is not a feed (an HTML events page, whatever its Content-Type) counts as `not_a_feed:<detected type>`.
4. Run `pnpm --filter collector test`. The seed-file test validates every city file and checks that no seed is denylisted.

The diagnose dry run 41856949627 changed the Atlanta seeds: the five The Events Calendar sites (Piedmont Park, Park Pride, the Atlanta Contra Dance Society, Alliance Theatre Offstage, ArtsATL) and the Atlanta History Center answer `?ical=1` with `X-Robots-Tag: noindex`, so they are page seeds that fall back to their HTML views and event pages; BeltLine's `?ical=1` answered with HTML, so it read its TEC list view as a page (later turned off: dry run 41871484438's page hints show beltline.org is a Next.js app whose list view has no Event markup, feed links or event links); the DeKalb, Gwinnett and Cobb libraries, Trees Atlanta, Atlanta Tech Village and Gwinnett parks have no event markup or feed links and are off; DeKalb County's events page serves a bot challenge and lists board meetings, so it is off. Marietta's CivicPlus feeds (several categories empty) and Kennesaw State's Localist API read fine; the Marietta seed lists no catIDs itself, so there was nothing to drop. The Atlanta seeds were written without network access from the authoring environment. The first live dry run (Actions run 41849155715) read Kennesaw State, Marietta and the Atlanta History Center; those are `verified: true`. The other endpoints were inferred from each site's platform and public search results and stay `verified: false` until a run reads them. Sites that answered 403 (City of Atlanta, Decatur) and sites with no machine-readable feed found (High Museum, Fernbank, the Center for Civil and Human Rights, Georgia Tech's RSS index, Emory's Trumba page until its web name is known) are off, with the reason in `note`. The Fulton County Library (BiblioCommons, a Crawl-delay over 60 s, no published feed, terms unread) is off too: a long Crawl-delay is honoured by the fetcher, but a seed is not added on the strength of that alone. Localist API reads need no key, but Concept3D says API use is licensed; ask each Localist calendar owner for permission (as D-037 does for Georgia State) and fall back to `kind: "page"` if they decline. Georgia State is left out because the D-037 importer already reads it.

## Ingest

Every source maps to one `feed_sources` row (migration 37, `collector = true`): the slug is the seed `id` (or `<api>-<region>` for an API adapter), the kind is the seed's (`page` seeds are kind `jsonld`), and the row records the attribution, the lane (`api`, `feed`, `page`), the seed city's region (point, radius, label, IANA timezone), the seed's `hubs` and when the job last sent it (`collector_seen_at`).

- **Route.** `POST /collector/ingest/events` on the collector Edge Function, `{run_id, source, items, seen?, complete, enable}`, at most 2,000 items and 2,000 seen ids, header `x-collector-secret` (the in-database secret of migration 28, the same scheme `places-extract.yml` uses). The function calls `collector_ingest_events(p_source, p_items, p_complete, p_enable, p_run_id, p_seen)`, service role only, and answers counts only (`first_error` stays in `feed_sources.last_error`).
- **Rows.** The RPC creates or updates the row from the seed. `p_enable` (staging) switches it on; without it a new row starts off and an existing row keeps its `enabled`, so production sources are switched on deliberately, never by the job. A seed with `enabled: false` switches its row off (the CLI syncs off seeds with no items). A slug owned by a non-collector source (the GSU partner rows) is refused (`source_not_collector`). Collector rows get no `import-feed` pg_cron job and are never dispatched to `import-feed`.
- **Items.** When the row is on, `import_upsert_batch` runs on the items: the events constraints, the content hash, cross-source dedupe (the same `import_title_key` or URL and start minute from another source links to the existing event), alcohol and 21+ items skipped (`age_21`: imported events are 18+), missed runs (an upcoming event missing from two complete runs is cancelled, unless a linked copy from another source is still listed, which takes over). An item without a usable point sits on the source's region point (`point_source = area_centroid`), and new events take the region's timezone.
- **Partial reads.** A batch is `complete: false` when any fetch for the source failed other than with an answer (`sources.ts` `isGap`): a 5xx, 429, 401/403, timeout, network error, robots.txt unavailable, a crawl delay too long, a host or crawl budget spent, the run deadline, too many redirects, an unsupported type, a response over the size cap, or bad JSON. Then `import_upsert_batch` counts no missed runs and cancels nothing (`partial: true` in its stats). A 404 or 410 on a side URL (not the source's first request), `noindex`, a robots.txt Disallow and the policy refusals (denylist, sign-in pages) are answers, so they keep the batch complete.
- **Retries.** The job retries a post on a 5xx. A second post for a source with the same `run_id` (`feed_sources.collector_last_run_id`) runs as a partial run (`repeat_run: true`), so a retry after a commit the job never heard back from cannot count a second miss in one run.
- **D-040 item rules in the database.** `collector_ingest_events` clips descriptions to 300 characters and drops `cover_url` unless the seed sets `imagesLicensed` (`feed_sources.images_licensed`), whatever the client sent. `enabled` is written only when it changes, so an ordinary post does not reschedule the import-feed pg_cron jobs. A set read from listing views and event pages (lane 3 behind a listing, and any seed with `crawlPages`) is a sample, never complete: the views are dated and capped, so an event missing from today's views may still be listed (staging run 41875345690: ArtsATL's dated views gave 12 of the 16 events 15 minutes after the first run, 4 counted missed). Missed runs and the two-miss cancellation therefore apply to feed-lane and API sources (Kennesaw State's Localist API, Marietta's CivicPlus feeds) and to page seeds whose own calendar-wide feed gave the events; lane 3 sources still cancel through `EventCancelled` markup and drop items once they end. A source that returned nothing at all never counts misses either.
- **Hubs.** `import_pick_hub`'s order: the lowest-priority matching keyword rule (`import_hub_rules`, matched on title, categories and host; the seed's `categories` are added to every item's), then the seed's first `hubs` entry that is an active 18+ hub (the row's `default_hub_id`), then the neutral Happening nearby hub. A seed test checks that every hub tag exists in `supabase/seed/hubs.sql` as a general 18+ hub.

### The workflow

`collector-ingest.yml` runs nightly (05:41 UTC) and on dispatch (inputs `region`, default `due`; `region_limit`, default 20; `max_run_minutes`, default 30 for regions and 9 for a city).

- **Regions (D-042 slice 6).** With `region` `due` (the schedule) the job asks the collector Edge Function for the collector regions not yet collected that UTC day (`GET /collector/regions?due=1&limit=20`, `collector_regions_due`, migration 45: point rounded to 0.1 degree, radius, label, zone; never a home count or a user id), from production when production posting is on and from staging otherwise. `all` takes every region. `pnpm --filter collector regions fetch` writes them to `work/regions.json` with any missing zone looked up offline (`tz-lookup`), adds the area of every city file that contains one of them as a seeds-only region (Atlanta's file is 60 km and its collector region 50 km, so its seeds keep their area; API adapters skip seeds-only regions and run once per collector region), and writes the discovered sources the database lists for them to `work/sources.json` (`GET /collector/sources?regions=<ids>`, D-042 slice 7; a 404 means the route does not exist yet and the run has city seeds only). `collect --regions-file … --sources-file …` runs a discovered source as a seed of its collector region (its row gets that region's point, radius and zone).
- **One pass.** Every region of a run is collected by one `collect` call with one `PoliteFetcher`, so the 2-second spacing, robots.txt, the 60-requests-per-host cap and the run deadline hold across regions, and a seed that two regions share is read once. The items of a source that fall outside tonight's regions go with its batch as `seen`, so nothing is cancelled because a neighbouring region was not due.
- **Record.** After the posts, `pnpm --filter collector regions record` stamps each collector region on the project it came from (`POST /collector/regions/record`, `collector_regions_record`): the UTC day, the sources that gave at least one item inside it and those items, and the zone looked up for it (stored only while the row has none and only if Postgres knows the name). A region with no item is still stamped, so it waits until the next day.
- **A city.** `region` set to a city file id (for example `atl`) runs that file's region only, as before slice 6.

It collects once (`--dry-run --diagnose --save`), then posts the saved batches (`--ingest --from`) to staging with `--enable`, and prints counts by source and hub plus what an Atlanta user sees (`supabase/tests/collector_ingest_counts.sql`, rolled back). It posts to production only from `main` and only when the repository variable `COLLECTOR_PRODUCTION` is `true` (default off), without `--enable`. It has no secret of its own: it links each project with `SUPABASE_ACCESS_TOKEN` and the database password, reads `collector_secret` from that project's vault, and masks it. Logs print counts and region ids, never a region's point. The HTTP cache (`packages/collector/.cache`) is kept with `actions/cache`. API keys (`TICKETMASTER_API_KEY`, `SEATGEEK_CLIENT_ID`, D-042 slice 10): the repository secrets, else the Edge Function secrets of the project the regions come from (`GET /collector/api-keys`), masked; the job takes the run's calls from the day's budget before collecting (`regions budget take`, `--api-budget`) and returns the unsent ones afterwards (`regions budget settle`). Without either key the lane is skipped and nothing is asked.

## Automatic source discovery (D-042 slice 8)

`pnpm --filter collector discover` (`src/discover-cli.ts`, `src/discovery/`) finds calendars for a collector region without a person writing seeds. Settings are in `data/discovery.json`.

- **Candidates** (`discover candidates`, design 6.1). For the collector regions due (`GET /collector/discovery/regions`, `source_discovery_regions_due`, migration 47: never built, or built over 30 days ago; 10 a night) the job pages the region's place tiles (`GET /collector/tiles/{id}/rows`, the rows the place files are built from) and keeps the `website` of event-likely kinds (library, school, arts venue, community, attraction, maker, dance, cinema, sports centre, historic, nature, park, market; bars, breweries and nightlife as a second tier). Restaurants, shops, cafés and places of worship never become candidates. One candidate per host (a leading `www.` dropped). Then Wikidata: the official website (P856) of the items those places link, 50 ids a SPARQL query and at most 5 queries, and one `wikibase:around` query (25 km) of museums, libraries, theatres, universities and colleges, concert halls, botanical gardens, parks, arts and community centres and cities (one `P279` hop), all through the PoliteFetcher's API lane with the bot's User-Agent. The cheap score is the kind prior times 20, plus 10 for a Wikidata item, plus 2 for each extra place that names the host (up to 10). Hosts of hand-written seeds and denylisted hosts are left out. At most 500 a region go to `POST /collector/candidates`, and the region is stamped (`POST /collector/discovery/regions/record`).
- **Probe** (`discover probe`, design 6.2). Candidates come from `GET /collector/discovery/queue` (`source_discovery_probe_queue`): the database refuses (`discovery_gate_closed`) unless this probe code passed the Atlanta gate within 30 days, and offers at most 150 a region a UTC day, less the probes already recorded that day. A probe sends at most 8 requests to a host (robots.txt included): robots.txt, the homepage, then up to 3 event pages. An event page is a same-site link (subdomains count, so `calendar.kennesaw.edu` is part of `kennesaw.edu`; also LibCal, Communico, Trumba and Localist hosts) whose path segment or host label is a keyword, or whose link text is one, in the region's languages plus English (`src/discovery/keywords.ts`); The Events Calendar's root from its head link (`…/events/?ical=1`), CivicPlus's `/iCalendar.aspx` and a deeper URL an OSM place gave come first. `/events/` and `/calendar/` (or the region's own words, `/veranstaltungen/` …) are guessed only when nothing matched. Platform marks are read from markup and URLs only: The Events Calendar, Localist, Trumba (`$Trumba.addSpud` to `trumba.com/calendars/<name>.ics`), CivicPlus, LibCal, Communico and Google Calendar embeds (to the public ICS). A Localist calendar is `needs_permission` and is not read. On The Events Calendar sites two of the calendar's single event pages are read first (their exports and list views often say noindex), and the source recorded is the calendar page, which the nightly run reads export first. The 8 requests count robots.txt and redirect hops (the shared fetcher gives each candidate host 8 a run; shared platforms such as Trumba, LibCal and Google keep 60). Otherwise the best seed (a calendar-wide feed, then a page with schema.org events, then the event pages) is read once through `collect()` with the probe's request cap, until one gives items inside the region; items without a point count as inside (they passed the region filter on the source's area). Results go to `POST /collector/sources/record` with run id `probe-<run>`.
- **Score** (design 6.3): the cheap score, plus 50 for a feed with events inside the region, 30 for a recognised platform, 40 for 3 or more schema.org events on a page, minus 30 when most items are outside the region. It orders the log; the queue is ordered by the cheap score stored with the candidate.
- **EU gate.** `euGate.countries` (the EU, the EEA and the UK, the same list as `source_discovery_allowed`) is read against the region's time zone (`src/discovery/eu.ts`; an unlisted `Europe/` zone or a missing zone counts as gated). Gated regions get no candidates and no probes until the attorney review; the database leaves their automatic candidates out of the queue as well while `meta.eu_discovery` is `off`.
- **Gate** (`discover gate`, design 6.4). Atlanta from scratch: candidates only from staging's Atlanta tiles and Wikidata, no seed URL, no stored candidate, an empty HTTP cache. The 150 best are probed, and the run passes when it finds a calendar (items inside the region, or Localist) on at least 6 of the 9 sites of the Atlanta seeds that are on today (`gate.expected`; a test keeps it equal to the enabled seeds of `atl.json`). The result is recorded under the probe code's hash (`src/discovery/version.ts`: every `.ts` file under `src/` plus the discovery and denylist data) with `POST /collector/discovery/gate`; any change to that code needs a new passing run before the probe reads candidates again.

`discovery.yml` runs the gate as a check on every push to a branch other than main and every pull request that changes the collector's code or data, and nightly at 02:19 UTC runs gate-if-needed, candidates and probes on staging (production only from main with the repository variable `DISCOVERY_PRODUCTION` set to `true`). The nightly collector run then reads probation and enabled sources (`GET /collector/sources`) and moves them on: a second good UTC day enables a source.

## Collector completion (migrations 62 and 63)

The plan, with the reasons, is `docs/design/collector/COLLECTOR_COMPLETION.md`. Slice 1 (database, collector package, workflows, Edge Functions) is built; the app, web and admin screens are Slice 2.

- **Listing removal.** `listing_removal_requests` and `submit_listing_removal` (service role only: the site's form route calls it after a Turnstile check, as NCII requests do since migration 54; 3 a day per email, 5 per client hash, 200 an hour). Moderators work through `mod_listing_removal_queue` and `mod_listing_removal_resolve`. Removing an item sets `event_imports.removed_at` on every import row of the event, so no source or linked copy republishes it; removing a source switches it off, marks it denylisted, adds its host to `collector_denylist` with reason `owner request <reference>` (never for a shared calendar host such as Google Calendar) and locks its discovery candidate. Those rows live only in the database: the nightly job reads them (`GET /collector/denylist`, `regions denylist`) and merges them into `data/denylist.json` for the run (`collect --denylist-file`). Contacts are cleared a year after a request closes.
- **Organizer claims.** `start_organizer_claim` gives a token (`ap-verify-` and 24 base32 characters) and three proofs: a `<meta name="activityplanet-verification">` tag or `/.well-known/activityplanet-verification.txt` on the claimed host, a DNS TXT record at `_activityplanet.<registrable domain>`, or the token in a connected calendar. The page and feed proofs are read by `collector verify` (`src/verify.ts`, `collector-verify.yml` every 30 minutes) through the PoliteFetcher with every rule (robots.txt included: a site that keeps the bot out uses the DNS proof); the DNS proof by the `organizer-verify` Edge Function over Cloudflare's DNS-over-HTTPS. A verified owner can set the default hub, hide an upcoming item, stop or resume the source, connect a feed and press Refresh now (`organizer_source_update`). A claim never makes imported items RSVP-able.
- **Connected feeds.** `connect_organizer_feed` makes an organizer-origin source (`org-<12 hex>`, kind ics) in the collector region of the owner's home; `GET /collector/sources` lists it for that region once the owner is verified, and its first good run switches it on. Eventbrite accounts connect through `eventbrite-connect` (key-gated; tokens in Supabase Vault, read only inside that function, which posts the events itself).
- **Venue geocoding.** `regions geocode` after the posts: our own places, then Geoapify with its key, then Nominatim (300 a night, Photon after a 429 or 5xx), each answer cached in `venue_geocodes` by `import_location_key` (`src/geocode/key.ts` is its twin). `import_upsert_batch` uses the cache before the area centroid.
- **Health.** Every collector workflow posts its run (`regions runs record`, `collector_job_runs`); `collector_ingest_events` counts a failing streak; `mod_collector_health` is the panel's data and `collector_health_alerts` (hourly) sends moderators in-app `collector_alert` notices, once a day per alert.
- **Open data.** `data/opendata/*.json` is a registry of event datasets with a box, licence and field map (`where` filters, `startFormat: text_range` for text dates); a dataset joins every run region its box overlaps. `opendata-scout.yml` (`opendata scout`, `opendata inspect`) finds and inspects candidates on the Socrata Discovery and ArcGIS Hub APIs, printing metadata and counts only. `collect --dataset <id> --dry-run --diagnose` live-checks one dataset.
- **Discovery tuning.** Kind priors (community 0.7, cinema 0.15, school 0.5), a Wikidata bonus of 25, and the learned yield of a kind once it has 30 probes worldwide (`GET /collector/discovery/yield`).

## Tests

`pnpm --filter collector test` runs on fixtures only, with a fake transport and a fake clock, and never touches the network. It covers:

- the API and open-data adapters

- an end-to-end run over a fixture site, and seed-file validation
